## 1. Executive summary — how the system works today

ai-server is a single-tenant, single-host job runner that turns natural-language asks, cron schedules and event triggers into **Claude Agent SDK sessions**, each parameterized by a `skills/<name>/SKILL.md` file. Everything the owner or the system launches becomes one `jobs` row in Postgres plus one id on the Redis list `jobs:queue` (`src/gateway/jobs.py:16-47`). One asyncio runner process (`src/runner/main.py`) holds a process-wide semaphore (default 4, prod 2), BLPOPs the queue only after it owns a slot (`main.py:143-151`), and calls the **single executor call site** `session_mod.run_session(job)` under a wall-clock timeout (`main.py:376-380`; default 1800 s, clamp 60-5400).

`run_session` (`src/runner/session.py:864`) does everything in one 1202-line module: it resolves the skill (kind→skill dir, fail-closed; `task` kind goes 30 regex rules → Haiku LLM classifier → generic, `session.py:587-647`), resolves cwd through the project delivery contract (`delivery.py:130-147`), decides an isolation tier (`workspaces.py:79-101`: none | workspace | host, tighten-only), clones a throwaway git workspace for workspace-tier skills (fail-closed, `session.py:922-948`), assembles a system prompt (server directive + job id + text-marker protocol + task transcript + skill body), and builds **one `ClaudeAgentOptions`** (`_build_options`, `session.py:650-816`) carrying model, effort, permission mode, allowed tools, in-session subagents compiled from other SKILL.md files, PreToolUse guard hooks, and in-process MCP servers (dispatch + projects). It then spawns the SDK-bundled `claude` CLI (2.1.139, 196 MB) as a subprocess speaking stream-JSON, iterates its messages, and mirrors them into a per-job append-only JSONL audit log and a Redis stream. The final assistant text is the deliverable: it is saved as `<job>.summary.md`, parsed for lifecycle markers (`TASK_COMPLETE:`, `TASK_QUESTION:`, `EVAL_PASS/FAIL:`, `<<<TASK_PLAN…>>>`), DM'd to Telegram, and stored as `Job.result.summary`.

**Containment is the SDK's hook protocol.** INV-17 (workspace containment) and INV-20 (read-only profile) exist only as `PreToolUse` hook callbacks the Claude CLI makes back into the runner on every tool call (`guards.py:381-490`, attached at `session.py:753/755`). They bind under `bypassPermissions` (53 of 72 skills). 48 of 72 skills run `isolation: none` — a shared checkout with no clone and no hooks — under a frozen 44-name allowlist in `scripts/lint_docs.py:612-635`. Only `god` is host-tier; kind=god is rejected at all three launchers.

**Quality loop.** After success, four post-steps run in order (`main.py:381-444`): DAG promotion, a *flag-only* post-session reviewer pinned to `claude-opus-4-7` (`review.py:250`), a CHANGELOG write-back check, and a Haiku learning extractor. The INV-13 merge gate is the *in-session* `code-review` subagent, whose verdict is never stored structurally. Failures escalate L0→1 (same skill, frontmatter `escalation.on_failure` model/effort) → L2/L3 `self-diagnose` (21 % of all jobs ever) → task failed. A retrospective auditor (`review-and-improve`, opus-4-7/max) runs whenever the queue is idle for 24 h and files `proposals` rows; 39 filed, 28 merged, 0 of the `default-model` kind.

**Surfaces.** Telegram (12 commands + buttons + thread replies; the only surface that creates a `Task`), a 200-line inline htmx dashboard behind one shared token, a REST/SSE API, per-job JSONL/summary files, and three out-of-band Telegram alerters (launchd bash ×2, Cloudflare Worker). Volume is dominated by machines: scheduler ~466, event-trigger 312, dispatch-MCP 234, web 219 vs Telegram 55 jobs lifetime.

**Atlas.** 40 of 72 skills and 32 of 41 schedules are the Atlas finance org. Trading follows "LLM proposes, kernel disposes": the only order path is `atlas/swing/swing/executor.py --submit` behind `risk.validate` (INV-22, docs + atlas tests only; no server-side deny). Today both auto-trading verticals are blocked on a missing `TRADIER_SANDBOX_TOKEN` (swing 37/37 runs `provisioning_gap`, value 0 theses) and the paper trader is degrading on stale Alpaca data (9 of 21 runs `stale_data`).

**Vendor posture.** Every LLM call in the repo is Anthropic via the subscription CLI: the main session, the in-session subagents, and four direct `query()` sites (router, learning, post-review, eval judge). There is no provider column, no cost column, one global quota pause key, and the model allowlist enforced by CI is the Telegram bot's alias table. INV-21 (multi-provider policy, owner-approved 2026-08-17) is a documentation row with zero code; the approved model-router plan's R0 is unstarted. The host is a 16 GB M4 Mac Mini with 3.8 GB swap in use, an idle Ollama holding 14 GB of stale weights, no off-site backup, and the atlas DB outside the nightly dump.

**The three structural facts a redesign must start from:** (1) there is exactly one executor and its options object, hook protocol, MCP bridge, message types and usage shape are all Claude-Code vocabulary; (2) the lifecycle protocol that sits *around* the executor — job row, Redis queue/stream/done contracts, audit event kinds, text-marker summary parsing, workspace clone + ff-sync, fail-closed skill resolution — is already vendor-neutral and load-bearing; (3) visibility is thin and text-shaped: no cost, no provider, no queue-wait, tool-level progress only via an SSE route nothing renders, and completion DMs that reach ~3 % of jobs.

### 2.2 Job lifecycle

**How it works.**
- Enqueue: all producers use `enqueue_job()` (`jobs.py:16-47`): INSERT `queued` row then RPUSH uuid to `jobs:queue` (`db.py:44`). Producers lifetime: scheduler ~466, event-trigger 312, dispatch-mcp 234, web 219, escalation 71, telegram 55, learning 42, bot-error-handler 42, deploy-autopilot 33, auto-continue 25, writeback 24, evaluator 11, owner-* ~25.
- Job loop (`main.py:113-185`): one `asyncio.Semaphore(max_concurrent_jobs)`; per tick SET `heartbeat:runner` (TTL 900 s), check `quota.is_paused()` (sleep 30 s if paused), acquire slot BEFORE `BLPOP` (2 s timeout). Strict FIFO, no priority, no per-kind cap.
- `_process_job` (`main.py:320-551`): fetch with retry delays (0/.2/.3/.5/1.0 s) because producers can make the id visible before the INSERT commits; on miss requeue to tail once. Flip queued→running; `_preflight_check` (`260-299`: task-continuation skill inheritance, cwd must exist); then `wait_for(run_session)`.
- Preflight and deploy-authority failures write ONLY a terminal `job_failed` (`main.py:364`) — no `job_started` (INV-2 carve-out, `SYSTEM.md:110`; spot-check).
- Success post-steps (`main.py:381-444`): `_finish_job(completed)` (publishes `jobs:done` BEFORE post-steps run) → refetch → `plans.promote_deferred_for` → `_maybe_review` (14/72 skills opt in) → `_verify_writeback` → `maybe_extract_learning` → `_update_task_after_job` if task_id.
- Task lifecycle (`main.py:1053-1266`): appends assistant TaskTurn, then READS THE JSONL AUDIT LOG for task_plan/task_question/task_choices/task_complete/eval_* events. plan → `plans.spawn_plan_jobs` (auto-approve); `_evaluate` result → task completed or fix round (max 2) then awaiting_user; task_complete → evaluator when `auto_evaluate`; no signal → auto-continue with sentinel description 'Continue to the next phase of the plan.' (one-level guard `1183-1186`).
- Plan DAG (`plans.py`): `validate_plan` (`62-110`, ≤12 subtasks, acyclic); roots `queued`, dependents `deferred` with `payload.depends_on` and no Redis entry; `promote_deferred_for` on every completion (task-scoped + task-less scan bounded to 200 rows); `fail_dependents_of` only when escalation exhausted. 32 rows carry depends_on; 14 `job_promoted` events.
- Failure branches (`main.py:446-551`) as in §2.1. Escalation (`704-853`): level tracked only in `payload.escalation_level`; L0→1 copies `escalation.on_failure.{model,effort}` (`main.py:759-760`; enqueue at `762-769`), L1→2 self-diagnose with audit excerpt, L2→3 effort=max, L3 task failed + cascade + `tasks:notify`. 80 rows carry escalation_level; 19 `escalation_spawned`.
- Quota: global pause; in 620+ prod log files there are 635 `rate_limit_status` events, 0 `rejected`, 0 `job_requeued_for_quota` — the pause path has never fired in production.
- Cancel: `cancel_job` publishes on `jobs:cancel`; `_cancel_listener` (`main.py:1368-1404`) calls `session.interrupt`; only running in-process jobs can be cancelled — queued ids are a no-op on this path.
- Scheduler (`main.py:1327-1362`, every 30 s): due unpaused rows → Job (created_by='scheduler', schedule_id), `flush`, RPUSH INSIDE the open transaction, `next_run_at` advanced from `now` (not the slot). One job per due schedule per tick; no misfire/catch-up.
- Event loop (`events.py:463-512`, every 60 s): circuit breaker (≥5 failures/10 min sharing an 80-char error signature → `events:breaker` TTL 1800 s + one self-diagnose); skill-failure rule (≥2 in 10 min → self-diagnose); multi-skill correlation; project unhealthy >20 min; idle-queue `review-and-improve` (24 h cooldown); idle-queue `alpha-governor` (4 h cooldown, <12 alpha-research/24 h — a server-side mirror of atlas `budget.yaml`).
- Reconcile (`reconcile.py`): at startup flip every `running` row to failed `error_category='orphaned'` unless the JSONL already has a terminal event ("last terminal event wins", `:131`; duplicates tolerated); `requeue_stranded_queued` RPUSHes `queued` rows absent from the list.
- Schedule adherence (`schedule_adherence.py`): pure `adherence_report` → DARK/NEVER_RAN/STUCK/FAILURE_STREAK; run out-of-band by launchd daily 07:15.
- Supervision (`main.py:1419-1486`): `_check_subscription_auth` → reconcile → four tasks (job_loop, scheduler_loop, cancel_listener, event_loop) under `wait(FIRST_COMPLETED)`; any exit is a crash → exit 1 → launchd restarts. SIGTERM drains in-flight.
- Schema (`models.py`): `jobs` (status CHECK 7 values via migration 006; payload/result JSONB; `ix_jobs_autotune(resolved_skill, resolved_model, resolved_effort, status)`), `schedules`, `tasks` (status String(20) no CHECK; `chat_id`, `thread_message_id`), `task_turns`, `projects`, `proposals`. Missing columns: provider, tokens, cost, num_turns, duration_api_ms, priority, lane, attempt (payload only), depends_on (payload only).

## 5. Visibility & ease-of-use gaps (consolidated)

**Cost, usage, provider**
1. No cost anywhere (`audit_log.py:12` "no cost"); no token columns on `jobs`; `usage` stored only as JSON in `result` and the `job_completed` event; 30-day totals derivable only by ad-hoc SQL.

3. `rate_limit_status` (636 events with utilization/resets_at) never aggregated; `/api/quota` shows only paused/reset_at/reason.
4. `_MODEL_BUDGETS` stale for 24 skills; context budget is a `len//4` estimate of the static prompt.

**Progress and completion**
5. Tool-level progress exists only on an SSE route (`web.py:599-640`) that takes the token in a URL and that no UI renders; Telegram gets lifecycle cards only.

9. No queue-wait, time-to-first-event, per-tool latency, or cancellation-latency measurement (INV-8 asserted, not measured).

10. Deliverables are truncated summary text (3500/3200/1500/1000/600/500 char caps); files written by skills get no URL or path; full summary only as raw JSON or `<job>.summary.md` on disk.

12. Web launches have no Task, so no plan/evaluator/approval/completion notifications.

**Commands and surfaces**
13. Ghost commands advertised in bot output and docs: `/rate`, `/status <prefix>`, `/cancel <prefix>`, `/proposals` — none registered; `cmd_status` ignores its argument.
14. `/clear` wipes the fleet without confirmation.
15. `/schedule add` requires raw cron on a phone; no delete/edit/run-now; no payload; list shows next run only.
16. Dashboard: inline HTML string with CDN htmx, raw-JSON job detail, no task/turn view (routes exist), no cancel button (DELETE exists), no schedule controls, 3-id model dropdown, single shared token rather than CF Access.
17. No canonical owner CLI/launcher; owner terminal work appears as ad-hoc `created_by` strings.
